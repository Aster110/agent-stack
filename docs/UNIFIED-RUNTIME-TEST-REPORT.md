## 实际实现

电脑、服务器和主脑均调用相同的 `runSeat`，使用同一个 `RealAppServerClient` 驱动。配置选择 `computer`、`server` 或 `brain`；主脑额外装配微信渠道，微信不再拥有第二套模型或会话核心。新 Codex 路径未使用 tmux。

Hub 与本地 relay 仍然是同一源码树中的独立网络组件。Claude App 继续使用已有 SSE 适配器；本轮未宣称完成新的 Claude 驱动或 App 验收。

## 真实 Codex 路径怎样验的

1. 从微信 HTTP 适配器输入新生成的随机内容，让真实 Codex 记住。
2. 通过真实本地 relay 的 mesh 消息提问；模型正确回忆微信输入，并把结果回给原 mesh 发送方。
3. 停止并重新启动新运行时，核对 thread ID 未变化。
4. 再从微信适配器要求创建文件；模型实际调用工具，文件内容与此前随机内容完全一致，回复走回微信适配器。
5. 检查测试过程中终端注入、终端启动和 tmux 调用次数为零。

这是跨渠道上下文与真实模型/工具验证。微信远端是测试替身，不能据此声称手机已经收到。两组测试也不构成一条真实手机→跨公网 Hub→电脑→原微信的完整验收。

## 本轮发现并修复的问题

| 问题 | 修正与验证 |
|---|---|
| 模型已完成但网络发送失败，可能误销账 | 完成结果持久化为待发；断线、重启、异常 HTTP 200 后补发，不重跑模型 |
| 提交任务后崩溃，可能重复执行副作用 | 调用引擎前写提交意图；实际 SIGKILL 故障测试确认恢复后不重做已发生的副作用 |
| 微信原始消息与游标分离，交接可能丢失 | SQLite 事务保存原始消息和游标；核心持久化接受后才完成交接 |
| 短期去重缓存淘汰、WAL 压缩后可能重做 | 独立持久化交接与任务结果去重；超过 1,000 条后重启仍拒绝旧消息重放 |
| 两个渠道各自排队，或发送卡住模型 | 同一线程串行、同一准入预算；发送结果不占用模型线程锁 |
| 异常结果信封可能变成新指令 | 先检查 result/system 信封；格式错误、发送方不匹配、无法关联任务、控制命令样式均不进入模型、不互相回执 |
| 主脑异步结果重启后回错地方 | 保存已验证回程；原任务记录暂不可用时仍按持久化回程补发 |
| 大整数 ID 被普通数字解析损坏 | 收信与确认 ID 保留原始完整整数，拒绝小数、指数等非法确认 |
| HTTP 200 被误认为微信已确认 | 必须解析有效对象、完整消息 ID 且无错误码；无确认时不前移分段进度、不销账 |
| 两个新进程同时写同一会话目录 | 本地 SQLite 独占锁；正常停止及 SIGKILL 后可重新取得锁 |
| 旧动态控制命令缺少完整恢复契约 | 候选明确关闭这些控制操作；固定配置席位仍可正常派单，能力恢复需单独验收 |

独立架构审查最终八项通过。此前红项已记录并修正；另有一次故障注入测试被新增去重保护挡住，随后让显式测试故障开关覆盖该保护，恢复了反例验证。测试超时曾出现在将大量模型轮次混入去重缓存验证的夹具，已改为真实消息交接与缓存淘汰验证，未将超时计为通过。

## 仍未完成的发布门槛

- 一个新用户从干净电脑和服务器出发，使用同一个发行清单完成安装、登录、配对和服务托管。
- 真实微信扫码、原用户收到文本和异步结果；附件/媒体按公布的支持范围验收。
- 真实跨公网 Hub 的整链路测试，以及断网、设备休眠和系统重启场景。
- 至少 48 小时实际运行观察；没有丢任务、错误回程、重复模型执行、意外换会话或持续增长的孤儿进程。本轮没有做出该时长声明。
- Claude App 的现有 SSE 接入回归、新运行时动态控制能力及原地迁移/回滚。
- 公开源码权限、许可证、私人默认值清理，以及新的 Node 24 安装器。

没有替换现有主脑或修改原电脑席位服务。候选仅在独立工作树、临时目录、独立端口和测试账号配置中运行；真实模型使用既有授权账号，微信没有接管现有账号的收信。

现有一键脚本仍是“安装前置条件”的旧基线，不能等同于统一候选的一键部署器。对外分享包目前只更新说明和证据，不伪装成已经发布的新系统。
